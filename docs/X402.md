# x402 integration guide — buying and selling on Mimir

Mimir sells oracle verdicts, premium prices, council votes and council reasoning
over **x402 v2** (`@x402/next`, `@x402/fetch`, `@x402/core`), in a
**Stellar-native `exact` scheme** implemented in
[`lib/x402/stellar-scheme.ts`](../lib/x402/stellar-scheme.ts). Prices live in
[`lib/x402/config.ts`](../lib/x402/config.ts); the seller paywall is
[`lib/x402/server.ts`](../lib/x402/server.ts); the buyer client is
[`lib/x402/buyer.ts`](../lib/x402/buyer.ts).

This guide is the contract for third-party buyers. It documents every paid
endpoint, the 402 quote, the payment proof, the freshness and replay rules, and
a working buyer example.

---

## How the scheme differs from EVM x402

On EVM, `exact` is a signed authorization a third-party facilitator submits and
pays gas for. On Stellar a ledger operation costs ~0.00001 XLM, so the buyer
just pays — and proves a payment that **already landed**:

1. Buyer requests a paid route unpaid and receives **402** with payment
   requirements (`{ amount, asset, payTo, network, … }`).
2. Buyer submits a classic Stellar `Payment` operation of at least `amount` in
   USDC to `payTo` and waits for Horizon to return the transaction.
3. Buyer signs a canonical proof message (Ed25519, the payer's own key) and
   retries with a `PAYMENT-SIGNATURE` header carrying
   `{ transaction, payer, signature }`.
4. Seller reads that transaction back off **Horizon in-process**: real,
   successful, recent, right asset, right amount, right accounts — then settles
   and returns the paid response with a `PAYMENT-RESPONSE` header.

There is no facilitator HTTP hop and no third party in the loop: "verify +
settle" collapses into "read Horizon". The seller-side scheme, facilitator and
local `FacilitatorClient` are all one module
([`lib/x402/stellar-scheme.ts`](../lib/x402/stellar-scheme.ts)).

## Paid endpoints

Every route is wrapped with `paidRoute("<priceKey>", …)`; the price constants
are `PRICES` in [`lib/x402/config.ts`](../lib/x402/config.ts). Amounts on the
wire are **USDC atomic units, 7 decimals** (1 USDC = `10_000_000`; see
[`lib/usdc.ts`](../lib/usdc.ts)).

| Method | Path | Price key (`PRICES`) | Price | Recipient |
|---|---|---|---|---|
| `GET` | `/api/premium/price?symbol=…` | `premiumPrice` | `$0.001` | platform seller (`SELLER_ADDRESS`) |
| `POST` | `/api/oracle` | `oracle` | `$0.005` | platform seller |
| `POST` | `/api/council/preflight` | `councilPreflight` | `$0.001` | the persona's own wallet |
| `GET` | `/api/council/reasoning?claimId=…&persona=…` | `councilReasoning` | `$0.001` | the persona's own wallet |
| `GET` | `/api/council/vote?claimId=…&persona=…` | `councilVote` | `$0.001` | the persona's own wallet |
| `POST` | `/api/council/subscribe` | `councilSubscribe` | `$0.01` | platform seller |

Notes:

- Council persona routes resolve `payTo` **per request** (from the `persona`
  query param) so each juror is paid directly into its own wallet.
- Settlement only happens when the handler returns a success status — a 4xx/5xx
  from the handler itself (e.g. an upstream 502 on the premium price route)
  costs the buyer nothing.
- Each paid route carries Bazaar discovery metadata (description, example
  input/output) so agents can enumerate these services; it is advertised via
  the `bazaar` extension on the facilitator's supported kinds.

## The 402 quote

An unpaid request gets **`402 Payment Required`** with a `PAYMENT-REQUIRED`
header: base64-encoded JSON with an `accepts` array of payment requirements.
Decoding it:

```ts
const quote = JSON.parse(
  Buffer.from(res.headers.get("payment-required")!, "base64").toString("utf8"),
);
const req = quote.accepts[0];
// {
//   scheme: "exact",
//   network: "stellar:testnet",          // CAIP-2, X402_NETWORK
//   asset: "USDC:GBBD47H6Y3P4GY…",       // classic asset id, NOT the SAC contract id
//   amount: "10000",                     // atomic units — $0.001 at 7 decimals
//   payTo: "G…",                         // where to send the USDC
//   maxTimeoutSeconds: 300,
//   extra: {
//     assetCode: "USDC",
//     assetIssuer: "GBBD47H6Y3P4GY…",
//     decimals: 7,
//     sacId: "C…",                       // Stellar Asset Contract id — advertised, never the match key
//     proofKind: "stellar-payment-v1",
//     maxAgeMs: 300000,                  // freshness window, see below
//   },
// }
```

The asset is deliberately the **classic** `CODE:ISSUER` id: verification reads
the payment back off Horizon, and a Horizon payment operation reports
`asset_code` + `asset_issuer`, never a SAC contract address. The SAC id in
`extra` exists only for Soroban-side buyers that want to move the same balance
through the contract; the seller never matches on it.

Network and asset constants:

- `X402_NETWORK` — `stellar:<network>` (defaults to `stellar:testnet`; override
  with the `X402_NETWORK` env var).
- `X402_SCHEME` — always `exact`.
- Asset — Circle Testnet USDC, 7 decimals.

## The payment proof

The retried request carries a `PAYMENT-SIGNATURE` header: base64 of
`{ x402Version: 2, accepted: <requirements>, payload: <proof> }`. The `payload`
is the proof itself:

```ts
interface StellarPaymentProof {
  kind: "stellar-payment-v1";   // STELLAR_PROOF_KIND discriminator
  network: string;              // e.g. "stellar:testnet"
  transaction: string;          // 64-char lowercase hex Stellar tx hash
  payer: string;                // G… account that sent the payment AND signed
  signature: string;            // base64 Ed25519 signature over the proof message
}
```

Everything else the seller needs (amount, asset, payTo) it already has in its
own requirements — reading those back off the buyer's payload would create a
second, forgeable source of truth. The Horizon ledger record is authoritative.

### The signed message (`paymentProofMessage`)

The signature is Ed25519 by `payer` over the **UTF-8 bytes** of exactly these
lines, joined with `\n` (no trailing newline) — matching
`paymentProofMessage()` in `lib/x402/stellar-scheme.ts`:

```
Mimir x402 payment v1
network: <network>
transaction: <transaction, lowercase hex>
payTo: <payTo>
amount: <amount, atomic units as a decimal string>
asset: <asset, CODE:ISSUER>
```

Concretely:

```ts
import { Keypair } from "@stellar/stellar-sdk";
import { paymentProofMessage } from "@/lib/x402/stellar-scheme";

const message = paymentProofMessage({
  network: requirements.network,      // from the quote, verbatim
  transaction: txHash,                // will be lowercased inside
  payTo: requirements.payTo,          // from the quote, verbatim
  amount: requirements.amount,        // atomic units, from the quote
  asset: requirements.asset,          // CODE:ISSUER, from the quote
});
const signature = keypair
  .sign(Buffer.from(message, "utf8"))
  .toString("base64");
```

Every value that decides whether the payment satisfies the quote is inside the
message, so a proof cannot be moved to a differently-priced resource; the
`Mimir x402 payment v1` header gives domain separation from signatures over
other Mimir surfaces (e.g. SEP-43 `signMessage`). G… addresses are
case-sensitive base32 — pass them through verbatim, never lowercased.

### What the seller checks (in order)

1. **Shape** — a well-formed `stellar-payment-v1` proof (64-hex transaction,
   valid `G…` payer).
2. **Network** — `proof.network === requirements.network`.
3. **Asset / payTo** — the quote is in USDC and `payTo` is a Stellar account.
4. **Signature** — Ed25519 verify by `payer` over `paymentProofMessage(...)`.
5. **Horizon transaction** — exists and was successful (404 → refusal;
   any other Horizon failure → refusal, never a guess).
6. **Freshness** — the transaction's age is within the window below.
7. **Payment operations** — the transaction contains at least one **plain
   `payment`** operation from `payer` to `payTo` in USDC (path payments don't
   count). Multiple matching operations in one transaction are **summed**.
8. **Amount** — summed paid ≥ quoted amount (overpayment is allowed; `exact`
   settles the quote, so the surplus is not booked as revenue for that call).
9. **Replay** — the transaction hash has not settled before (see below).

Refusals surface as `invalidReason` / `errorReason` values: `malformed_proof`,
`network_mismatch`, `unsupported_asset`, `unsupported_pay_to`,
`invalid_signature`, `transaction_not_found`, `transaction_failed`,
`payment_too_old`, `no_matching_payment`, `insufficient_amount`,
`already_settled`, `horizon_unavailable`.

### Freshness window

A Stellar transaction hash is public and permanent; without an age bound,
yesterday's payment would keep buying today's responses. A proof is accepted
only while the underlying payment is at most
**`X402_PAYMENT_MAX_AGE_MS`** old — default **5 minutes**
(5 × 60 × 1000 ms), overridable via the env var of the same name. That is
comfortably longer than a ~5s ledger close plus the buyer's round trip, and
short enough that a harvested proof is not worth chasing (and the payer's own
signature would stop it anyway). Stale proofs are refused with
`payment_too_old` during settle, before any response is produced.

### Replay rules

A landed hash can be **presented** many times even though it can only be
**submitted** once. Each transaction hash buys exactly **one** response,
enforced in `consumeSettlement()` with two layers:

- **In-process** — a bounded set (max 4096 entries, far above what one
  freshness window can produce) claimed before the durable check, closing the
  gap between settle and the ledger write on this instance.
- **Durable** — a `payments_v2` row keyed by
  `(network, payment_identifier)` where the identifier is the lowercased
  transaction hash. This survives process restarts and covers a second
  serverless instance. Without `DATABASE_URL` only the in-process layer exists.

A second presentation of a settled hash is refused with `already_settled` —
both at `verify` (read-only check) and at `settle` (the claim). The payments
ledger's unique index is accounting idempotency (`ON CONFLICT DO NOTHING`),
**not** the replay defence; the claim happens before the paid response exists.

### The paid response

A settled purchase returns the handler's normal response plus a
`PAYMENT-RESPONSE` header: base64 JSON with settlement metadata —
`{ success: true, transaction, network, payer, amount }`, where `amount` is
the **quote**, in atomic units, and `transaction` is the Stellar tx hash (also
the ledger's payment identifier). Handlers may additionally trust the payer:
`paymentPayer(req)` reads the `G…` address back out of the already-verified
`PAYMENT-SIGNATURE` header.

## Council passes (`POST /api/council/subscribe`)

One payment can buy a **window of free council reasoning reads** instead of a
single read:

```bash
curl -X POST https://<host>/api/council/subscribe   # unpaid → 402; paid retry → 200
```

A paid `POST` (price: `councilSubscribe`, `$0.01`, paid to the platform
seller) returns:

```json
{
  "plan": "council",
  "payer": "G…",
  "pass": "<signed token>",
  "expiresAt": 1760000600000,
  "ttlMs": 600000,
  "price": "$0.01"
}
```

The pass is bound to the payer of the payment. Present it on reasoning reads —
no per-request payment is taken while it is valid:

```
GET /api/council/reasoning?claimId=12&persona=optimist&pass=<pass>
```

Default TTL is 10 minutes (`COUNCIL_PASS_TTL_MS` to override). This is a
bundled-access tier on top of per-request x402, deliberately not a recurring
subscription.

## Buyer example (`lib/x402/buyer.ts`)

The in-repo buyer wraps `@x402/fetch` with a **hard budget cap**. The cap is
load-bearing: under this scheme the buyer submits its own payment, so by the
time a payload exists the money is gone — the cap therefore runs inside the
payment-requirements policy, **before** any payment is created. An over-budget
quote throws `PaymentBudgetExceeded` and no USDC leaves the wallet.

```ts
import { fetchWithBudget, payingWalletFor, PaymentBudgetExceeded } from "@/lib/x402/buyer";
import { PRICES, priceToUsdcUnits } from "@/lib/x402/config";
import { walletFromKeypair } from "@/lib/agent-wallets";
import { Keypair } from "@stellar/stellar-sdk";

const wallet = walletFromKeypair(Keypair.fromSecret(process.env.BUYER_SECRET!));
const payer = payingWalletFor(wallet);

// Cap at twice the list price, in USDC atomic units (7 decimals).
const cap = priceToUsdcUnits(PRICES.premiumPrice) * 2n;

try {
  const { response, payment } = await fetchWithBudget(
    `${BASE}/api/premium/price?symbol=bitcoin`,
    payer,
    cap,
  );
  // response.status === 200; payment === { priceUnits, txHash } for a settled buy
} catch (error) {
  if (error instanceof PaymentBudgetExceeded) {
    // Too expensive — walked away WITHOUT submitting a payment.
  }
}
```

`priceToUsdcUnits` converts a dollar string (`"$0.001"`) to atomic units.
`payingWalletFor` builds a fresh `x402Client` per purchase (policies are
per-capsule), registered for exactly `exact` on `X402_NETWORK` — a quote for
any other chain never reaches the paying scheme. For an uncapped fetch (only
appropriate when the caller controls the URL and price), `createPayingFetch`
returns a `fetch` that auto-pays any 402.

A third-party buyer outside this repo can do the same with plain HTTP:

1. `GET`/`POST` the route → decode `PAYMENT-REQUIRED`.
2. Submit the USDC `Payment` on Stellar, wait for Horizon.
3. Sign `paymentProofMessage(...)` with the payer key; retry with
   `PAYMENT-SIGNATURE: base64(JSON.stringify({ x402Version: 2, accepted, payload }))`.
4. Read the paid body and the `PAYMENT-RESPONSE` settlement metadata.

Live proof of this exact flow (quote → pay → replay refusal → ledger row):
`npm run smoke:x402:http` against a dev server
([`scripts/x402-http-smoke.ts`](../scripts/x402-http-smoke.ts)).

Buyers pause independently of sellers: `MIMIR_PAUSE_X402_BUYING=1` (or the
global `MIMIR_PAUSE_ALL`, or a per-address entry in `MIMIR_PAUSED_X402_BUYERS`)
makes `lib/x402/buyer.ts` refuse to spend.

## Seller kill switch (`x402_selling`)

Paid endpoints pause independently of the rest of the app — if Horizon is
degraded, a verifier that cannot read the ledger must refuse rather than guess,
while market settlement and withdrawal keep working. The capability is
`x402_selling` ([`lib/ops/flags.ts`](../lib/ops/flags.ts)):

```bash
MIMIR_PAUSE_X402_SELLING=1     # pause selling paid endpoints
MIMIR_PAUSE_ALL=1              # global pause, reaches x402_selling too
```

While paused, every paid route answers **`503`** with
`{ error: "paid endpoints are temporarily unavailable", detail: … }` and a
`Retry-After: 60` header — deliberately 503 and not 402, because a paying agent
that sees a 402 will try to pay.

## Configuration reference

| Env var | Meaning | Default |
|---|---|---|
| `SELLER_ADDRESS` | Default recipient for platform-sold routes | required |
| `X402_NETWORK` | CAIP-2 network the scheme settles on | `stellar:<network>` (e.g. `stellar:testnet`) |
| `X402_PAYMENT_MAX_AGE_MS` | Freshness window for a payment behind a proof | `300000` (5 min) |
| `COUNCIL_PASS_TTL_MS` | Council pass lifetime | `600000` (10 min) |
| `MIMIR_PAUSE_X402_SELLING` | Kill switch for all paid routes (`x402_selling`) | unset (selling) |
| `MIMIR_PAUSE_X402_BUYING` | Kill switch for `lib/x402/buyer.ts` | unset (buying) |
